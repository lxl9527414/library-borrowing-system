# AI 性能与成本报告

> 测试时间：2026-11-02
> 被测版本：`b1ab000`（W3 完成）
> 测试性质：**真实模型 + 真实检索 + 真实工具链路**的延迟与成本测量，非压测（并发能力见 [质量与性能数据.md](质量与性能数据.md)）
> 目的：把「AI 功能贵不贵、快不快」变成可复核的数字，而不是"感觉还行"

---

## 1. 测什么、为什么这么测

AI 应用的性能不能只看"模型快不快"，它分成三层，每层都会叠加到用户感知上：

```text
用户按回车
   │
   ├─ ① 模型层：首 token 延迟（TTFT）—— 决定"多久开始出字"
   ├─ ② 编排层：Agent 多轮工具调用 + 检索 + 重排 —— 决定"总共等多久"
   └─ ③ 成本层：每次对话消耗多少 token —— 决定"用得起用不起"
```

三层分别测：① 直连模型基准（`scripts/bench_llm.py`）、② 端到端真实问答（85 条评测集）、
③ 从 ② 的真实 token 用量反算。

---

## 2. 测试环境

| 项 | 配置 |
|---|---|
| 机器 | MacBook（Apple Silicon），本机运行全部组件 |
| 模型 | DeepSeek `deepseek-chat`（`https://api.deepseek.com/v1`，OpenAI 兼容） |
| embedding | 通义 `text-embedding-v3`（1024 维），索引 535 块 |
| AI 服务 | Python 3.10 / FastAPI / LangGraph 1.2.19，单进程 uvicorn |
| 业务后端 | Spring Boot 3.5（本机 18080），工具调用走 HTTP 内网 |
| 网络 | 公网 → DeepSeek / DashScope（国内直连，无代理） |

**测试局限（先声明）**：

1. 只有单机、单并发（并发能力不是本报告目标）；
2. 公网模型延迟受运营商与模型服务排队影响，**数字有波动**，所以我用多次采样 + 分位数，而不是单次结果；
3. 模型价格会调整，成本按 **2026-11 官方价目**换算（见 §5），换价只需改一个常量。

## 3. 第一层：模型直连基准（12 次采样）

命令：`ai-service/.venv/bin/python scripts/bench_llm.py --samples 12`

| 指标 | 结果 |
|---|---|
| **TTFT（首 token 延迟）** | **P50 897 ms / P95 1,186 ms**（min 726 ms，max 1,186 ms） |
| 完整响应耗时 | P50 1,701 ms / P95 2,145 ms |
| 输出速度 | **84.2 字/秒** |
| 单次 token | 输入 22 / 输出 93（短问答） |

**怎么读这组数字**：TTFT ≈ 0.9 s 是"用户按下回车到看见第一个字"的等待，配合前端的打字机效果，
体感上接近"立即响应"；而完整回答 1.7 s 左右结束，读者不需要干等。

> 早期单次测量的 TTFT 是 521 ms（网络好时），说明这层波动较大，**看 P95 更真实**。

## 4. 第二层：Agent 端到端（85 条真实问答，走完整链路）

每条用例都真实经过：`浏览器 SSE → AI 服务 → LangGraph → 工具调用（Java 内网 / 向量检索）→ 模型 → 流式回传`。

| 指标 | 值 |
|---|---|
| 采样数 | 85 条（book 30 / faq 30 / rule 15 / 拒答 10） |
| **端到端 P50** | **2,481 ms** |
| **端到端 P95** | **10,654 ms** |
| 平均（健康样本 77/85） | 3,140 ms |
| 平均（含重试/超时） | 5,527 ms |
| 触发知识库检索的轮次 | 63 / 85（74%） |

**分类别看**：

| 类别 | 平均 | P95 | 说明 |
|---|---|---|---|
| 拒答类 | 2,295 ms | 3,536 ms | 直接拒答，最轻 |
| faq（流程） | 3,035 ms | 3,754 ms | 检索 1 次 + 短回答 |
| rule（规则） | 4,264 ms | 11,521 ms | 检索 + 需要核对数值，输出更长 |
| book（馆藏事实） | 9,729 ms | 40,992 ms | **多轮工具调用**（先查库存再查详情），输出最长 |

**为什么 book 类慢**：模型会连续调用 `search_books`（有时两次，先查书名再确认库存），
每次工具调用都是一次"模型思考 + 内网往返"，所以延迟是 faq 的 3 倍。
P95 的 40 s 来自个别网络重试（见 §6 局限），不代表正常路径。

## 5. 第三层：成本

### 5.1 单轮对话的 token 结构（85 条实测）

| 项 | 平均 | 最大 |
|---|---|---|
| 输入 token | **4,054** | 10,913 |
| 输出 token | **165** | 615 |

**关键发现：成本 96% 花在输入，而不是输出。** 输入里包含：系统提示词（7 个工具定义 + 引用规则）、
工具返回结果（馆藏列表 / 检索块）、多轮对话历史。

### 5.2 单价与换算（DeepSeek 官方价目，2026-11）

| 项 | 单价 | 说明 |
|---|---|---|
| 输入 | ¥2 / 百万 token | 缓存未命中；命中时约 ¥0.5 / 百万 |
| 输出 | ¥8 / 百万 token | — |
| embedding（通义 text-embedding-v3） | ≈ ¥0.5 / 百万 token | 建索引与查询共用 |
| rerank（通义 gte-rerank-v2） | ≈ ¥0.8 / 百万 token | 按候选文本计费 |

### 5.3 单轮与规模化成本

| 场景 | 计算 | 成本 |
|---|---|---|
| **单轮对话** | 4054 × ¥2/M + 165 × ¥8/M | **≈ ¥0.0094** |
| **每千次对话** | ×1000 | **≈ ¥9.42** |
| 每万次对话 | ×10000 | ≈ ¥94 |
| embedding 建索引（一次性） | 535 块 × ~100 token × ¥0.5/M | ≈ ¥0.027 |
| 每次查询 embedding | ~20 token | ≈ ¥0.00001 |
| 每次重排（20 候选，当前默认关闭） | ~6,000 token × ¥0.8/M | ≈ ¥0.0048 |

**结论**：一个学生项目的演示规模（每天几十次对话），DeepSeek 方案**月成本在个位数人民币**；
即使日活 1000 人、每人 5 轮，月成本约 ¥1,400。真正的成本风险不在单价，而在
**Agent 死循环 / 工具结果过长 / 上下文无限增长**——这三件事都必须有硬约束（已实现最大步数 8、
工具结果截断、会话摘要）。

### 5.4 降本手段（按性价比）

| 手段 | 预期效果 | 状态 |
|---|---|---|
| 语义缓存（相似问题命中缓存） | 高频问题省 30%~50% | 未实现（W4 可选） |
| 工具结果截断（检索块 ≤500 字、列表 ≤20 条） | 输入已从 ~6k 降到 4k | ✅ 已实现 |
| 限制 Agent 最大轮数（8） | 防止失控成本 | ✅ 已实现 |
| 会话摘要压缩（超长对话自动摘要） | 长会话输入线性增长 → 有界 | 未实现 |
| 关闭重排（当前默认） | 每轮省 ¥0.005 | ✅ 默认关闭 |

## 6. 稳定性观察（必须如实说）

85 条用例首次全量跑时，**25 条因 `Connection error` 失败**（DeepSeek 侧连接中断，非本地异常），
重试补跑后全部完成。这说明：

1. 真实模型服务的**网络稳定性是系统可用性的一部分**，必须有重试 + 降级（当前网关有重试与 fallback 链）；
2. 评测/批处理场景需要**断点续跑**，不能整段重跑（当前 `eval_answers.py` 是失败重跑整段，已列为改进项）；
3. 前端体验上，流式输出 + 已收到部分内容时不盲目重试，避免"回答重复两遍"。

## 7. 复现

```bash

cd ai-service && .venv/bin/python scripts/bench_llm.py --samples 12

# 2) 端到端 85 条（真实模型 + 真实检索，约 20~40 分钟，含重试）

# 3) 成本反算：读 eval/eval_report_answers.json 里的 usage 字段
```
