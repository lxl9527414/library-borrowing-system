## 1. 简历项目段（推荐版，约 5 行）

> **AI 原生图书借阅系统**（个人项目 / 2026.10–2026.11）
> 技术栈：Java 17 · Spring Boot 3.5 · Python 3.10 · FastAPI · LangGraph · RAG · 通义/DeepSeek · Redis · Vue 3 · Docker · GitHub Actions
> - **Agent 工程**：基于 LangGraph 实现「agent → 授权 → 工具 → agent」状态机，将借书/还书/预约等 7 个业务能力工具化；写操作经 `interrupt` 暂停、前端确认后才执行，并对越权操作做服务端拦截（端到端 16 项断言覆盖身份透传/确认/落库）
> - **RAG 全链路**：自建 535 块知识语料，通义 embedding（1024 维）向量索引 + BM25 混合检索 + gte-rerank 重排；向量检索使规则类 MRR 由 0.394 提升至 0.578，Recall@5 达 1.000
> - **答案质量**：实现引用溯源（正文 `[n]` → 来源卡片）与无依据拒答；自建 85 条评测集与 RAGAS 等价指标（LLM-as-judge），faithfulness 0.940、引用准确率 0.913、拒答 9/10
> - **工程与成本**：71 个后端单测 + 319 个 AI 服务单测全离线可跑；GitHub Actions 五 job 门禁（含密钥扫描与 RAG 召回阈值）；实测首 token 延迟 P50 897 ms、单轮成本约 ¥0.0094

**如果你简历空间紧，只留三条**：Agent 工程、RAG 全链路、答案质量（工程与成本并到第三条尾部一句）。

## 5. 30 秒口述稿（自我介绍 / 面试开场）

> 我的项目是一个图书馆借阅系统，原本是 Spring Boot 的 CRUD 项目。我在上面加了一层 AI 应用：用 LangGraph 把借书、还书、预约这些真实业务做成工具给模型调用，写操作必须用户确认才执行；另外做了 RAG 知识问答，能带引用回答借阅规则，没依据时会拒答。为了证明有效，我建了 85 条评测集——检索 Recall@5 是 1.0，答案 faithfulness 0.94，引用准确率 0.91；首 token 0.9 秒，单轮成本不到 1 分钱。整套 319 个单测离线可跑，CI 会拦回归。

## 6. 90 秒版（面试官说"展开讲讲"）

1. **为什么加这一层**：原系统功能完整但没有 AI 能力，与岗位不匹配；我不想只贴一个聊天框，而是让 AI 真正能操作业务数据。
2. **关键设计**：AI 不直连数据库，身份只从 token 解析，写操作必须确认——这三条决定了它"能干活但不会闯祸"。
3. **RAG**：535 块语料 + 向量/混合检索 + 重排，规则类问题从"被 FAQ 抢位"（MRR 0.394）到 0.578。
4. **怎么证明有效**：检索层（Recall@5/MRR）+ 答案层（faithfulness/引用准确率/拒答），都是可复现命令。
5. **工程化**：mock 让 319 个测试离线跑、CI 五 job 门禁、SSE 流式与前端确认/引用。
6. **我最大的收获**：AI 功能的价值不在"调通模型"，而在**可验证、可回滚、可解释**。

## 7. 简历 "项目难点" 栏可写的三条（真实且能展开）

| 难点 | 怎么解决的 |
|---|---|
| 真实模型会"跨轮"直接调写工具，只带 bookId，确认卡片拿不到书名 | 确认前回查详情接口补书名（只读幂等 + 缓存），并给无书名兜底文案 |
| 重排反而让指标变差 | 排查发现重排只看到 top-5 候选，改为先取 20 候选再重排；剩余差距定位到评测口径（rule/FAQ 多源等价），如实记录而非调参刷分 |
| 生产构建下 `/chat` 404（Vite dev 正常） | 定位到 `SpaController` 路由白名单硬编码，补路由并加注释约束，避免下次再犯 |
