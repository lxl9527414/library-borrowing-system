# 技术决策记录（ADR）

> 记录"为什么这么做"，而不是"做了什么"。面试时被追问"为什么不用 X"时，这里就是答案。
> 每条格式：背景 → 选项 → 决策 → 代价（我接受了什么）。

---

## ADR-001　Java 业务层 + Python AI 服务（双栈，而不是单栈）

**背景**：已有 Spring Boot 业务系统（RBAC、事务、预约队列、AOP 日志），要加 Agent/RAG 能力。

**选项**
- A. 全 Java：Spring AI / LangChain4j
- B. 全 Python：把业务重写一遍
- C. 双栈：Java 保留业务，Python 做 AI 编排

**决策**：C。

**理由**
1. 业务逻辑（库存扣减、借阅上限、预约顺延）已在 Java 里被测试和线上验证过，重写是净损失；
2. AI 应用岗的 JD 与生态（LangGraph、RAGAS、evaluation 工具链）主流在 Python；
3. "跨服务工具调用 + 身份透传"本身就是真实的工程问题，能讲出深度。

**代价**：多一个运行时、多一套部署（用 docker-compose 与 dev_up.sh 抵消）；跨服务调试更麻烦。

## ADR-002　AI 不直连数据库，所有写操作回到业务层

**背景**：Agent 要执行"借书/还书/预约"，最省事的做法是让 Python 直接连 MySQL 改状态。

**选项**
- A. Python 直连 DB（快，但绕过事务与权限）
- B. 通过业务层内部 API（多一跳网络）

**决策**：B。

**理由**：业务规则（借阅上限、库存并发、预约优先级）只能有一个事实来源；AI 层复制一遍必然会分叉。
同时把身份校验留在 Java（token → `UserSession`），LLM 无法伪造 userId。

**代价**：每次工具调用多一次内网 HTTP + Redis 校验（实测工具调用 10~50 ms，可接受）。

## ADR-003　写操作必须"人在回路"确认（而不是让模型直接执行）

**背景**：LLM 会幻觉参数，也可能误判用户意图（"帮我把这本书还了"到底还哪本？）。

**选项**
- A. 直接执行，出错再回滚
- B. 生成"待执行动作"，用户确认后才执行

**决策**：B（LangGraph `interrupt` + 前端确认卡）。

**理由**：图书馆场景的写操作有真实后果（库存、罚金、预约队列）；一次误操作要人工修数据。
确认卡还顺便把"AI 在做什么"可视化，降低用户不信任感。

**代价**：多一次交互；`interrupt` 的恢复要求节点无副作用（由 `authorize` 节点纯计算+重放置换保证）。

## ADR-004　默认 mock 模型，真实模型可选

**背景**：没有 API Key 时（CI、他人 clone、离线演示）系统要能跑；有 Key 时要能一键切真模型。

**选项**
- A. 只支持真实模型（无 Key 就跑不起来）
- B. 内置确定性 mock + 真实 provider 可切换

**决策**：B。

**理由**：319 个离线测试、CI、演示截图都可以零成本复现；mock 的确定性让 SSE/确认流程可以精确断言。

**代价**：mock 只能按关键词应答，会被误认为"AI 很笨"——已通过 UI 徽标、tooltip、兜底文案明确声明它是离线模式
（这个坑真实发生过，见 `docs/AI-架构与接口契约.md` §10.6）。

## ADR-005　RAG 向量存储：pgvector 为目标形态，numpy 为降级实现

**背景**：本机 Docker 拉不到 pgvector 镜像，但线上/演示环境希望用成熟方案。

**选项**
- A. 只做 pgvector（本机跑不起来）
- B. 只做内存向量（部署要重新实现）
- C. 抽象 `VectorStore` + 双后端

**决策**：C（`NumpyVectorStore` 默认，`PgVectorStore` 连不上自动降级）。

**理由**：535 个块在内存里做余弦完全够用；抽象层保证换后端不改业务代码。

**代价**：两套实现要同步维护；numpy 版无法水平扩展（单实例内存有上限）。

## ADR-006　重排用通义 `gte-rerank-v2`，而不是"让 LLM 输出 JSON 排序"

**背景**：需要把 20 个候选重排到 5 个。

**选项**
- A. LLM listwise（让模型输出 `{"ranking":[...]}`）
- B. 专用 cross-encoder 重排 API（gte-rerank-v2）

**决策**：B（LLM listwise 作为可选 provider 保留）。

**理由**：LLM 输出格式会漂移（代码块、自然语言、越界编号），解析失败率与成本都更高；
cross-encoder 返回结构化 `index + relevance_score`，单次 ~240 ms，便宜且稳定。

**代价**：多一个供应商依赖；实测在当前评测集上重排**没有超过纯向量**（0.902 vs 0.916），
原因是 rule/FAQ 多源等价 + 8% 调用失败（已如实写入评测报告，未在测试集上调参）。

## ADR-007　答案层评测自研 RAGAS 等价指标，而不是装 ragas 库

**背景**：需要 faithfulness / answer relevancy / context precision。

**选项**
- A. `pip install ragas`
- B. 自研指标 + LLM-as-judge

**决策**：B。

**理由**：ragas 依赖 `datasets`/`tiktoken`，tiktoken 首次运行需联网下载 BPE（本机网络受限，实测不可行）；
自研只需 1 次 judge 调用/用例，指标定义可追溯、成本可控（DeepSeek 价格极低）。

**代价**：指标与 RAGAS 官方实现不逐字一致（已注明"等价实现"）；judge 与生成模型同源存在自评偏好。

## ADR-008　流式用 SSE，而不是 WebSocket

**背景**：Agent 回答是流式的，且需要传递工具调用、确认请求等结构化事件。

**选项**
- A. WebSocket（双向）
- B. SSE（服务端单向推送）

**决策**：B。

**理由**：交互本质是"一次请求 → 多个事件"的单向流；SSE 天然带事件名、可被 nginx/HTTP 中间件透明转发、
断线重连语义简单；权限仍用普通 `Authorization` header（WebSocket 握手带 header 更麻烦）。

**代价**：确认操作需要**另发一个 HTTP 请求**（`/api/ai/chat/confirm`），不能在同一条连接里回传；
已用"确认卡 + 独立请求"设计消化。
