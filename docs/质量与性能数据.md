# 质量与性能数据

> 本文合并了三份过程文档（单元测试与覆盖率、压测报告、CI 说明），保留可复现的数字与结论。
> 数据时间：2026-11-02/03；环境：本地开发机（测试）+ 阿里云 ECS 2C1.76G（压测/部署）。

## 1. 测试矩阵

| 层 | 数量 | 命令 | 是否离线 |
|---|---|---|---|
| 后端单元测试（JUnit 5 + Mockito） | **71** | `cd backend && mvn -B clean test` | ✅ 不需要 MySQL/Redis/网络 |
| AI 服务测试（pytest） | **319** | `pytest ai-service -q` | ✅ mock LLM + fakeredis + MockTransport |
| Agent 端到端 | 16 项断言 | `python scripts/e2e_ai.py` | 需本地服务（真实模型可选） |
| RAG 端到端 | 5 类问题 | `python scripts/e2e_rag.py` | 需本地服务 |
| UI 回归 | 截图走查 | `node scripts/ui_screenshot.mjs` | 需 headless Chrome |

**为什么能离线**：三层替身——Mock LLM（确定性关键词模型）、fakeredis、`httpx.MockTransport`；CI 不需要任何 API Key。

## 2. 后端覆盖率（JaCoCo 0.8.12）

运行：`cd backend && mvn -B clean verify` → 报告在 `backend/target/site/jacoco/index.html`

### 2.1 总体

| 指标 | 覆盖 | 说明 |
|---|---|---|
| 指令 | **55.2%**（2078/3765） | — |
| 分支 | **48.4%**（149/308） | — |
| 行 | **58.1%**（467/804） | — |
| 方法 | **45.7%**（74/162） | — |
| 类 | **64.1%**（41/64） | — |

### 2.2 核心业务类（行覆盖）

| 类 | 行覆盖 | 分支覆盖 |
|---|---|---|
| `BorrowRuleService` | **100.0%** | 100.0% |
| `AiToolService` | **100.0%** | 80.0% |
| `BorrowService` | **91.2%** | 64.1% |
| `ReservationService` | 69.8% | 61.1% |
| `BookService` | 57.6% | 72.2% |

### 2.3 覆盖率的诚实解释

- 未覆盖的 0% 包集中在 `controller`、`config`、`security`、`task`、`Dashboard/Auth/UserService`——这些要么逻辑薄（DTO 转换），要么依赖完整 Spring 上下文/Redis，更适合用 e2e 覆盖；
- **核心规则（借阅上限、罚金、预约顺延、AI 工具）覆盖率 90%+**，这是有意的取舍：测试预算花在业务风险最高的地方；
- 覆盖率不是越高越好，**"关键路径全覆盖 + 全链路 e2e"** 比刷总数字更有价值。

## 3. 只读压测

### 3.1 环境与方式

| 项 | 值 |
|---|---|
| 环境 | 阿里云 ECS 2C / 1.76G 混部（MySQL + Redis + Java + Python 同机） |
| 工具 | `docs/loadtest.py`（Python 线程池，仅 GET，只读，无写操作） |
| 梯度 | 并发 1（预热）/ 10 / 25 / 50，每场景 15 秒 |
| 接口 | 图书列表 / 我的借阅记录 / 工作台统计 |

### 3.2 汇总结果

| 指标 | 数值 |
|---|---|
| 总请求数 | **11,275**（含预热 226） |
| 失败请求 | **0**（成功率 100%） |
| 单请求延迟（并发 1） | 32–63 ms，P99 < 140 ms |
| 最优工作点 | 并发 **10**：83–99 QPS，P99 175–351 ms |
| 峰值吞吐 | 借阅记录 109.8 QPS / 图书列表 92.6 QPS / 工作台 52.5 QPS（并发 50） |
| 吞吐拐点 | 并发 10 左右（10→25→50，QPS 仅从 83 涨到 93） |

### 3.3 瓶颈定位

| 观察 | 值 | 结论 |
|---|---|---|
| CPU 用户态 | **92%–95%** | CPU 已打满 |
| CPU 空闲 | 0%–2% | 无余量 |
| 运行队列 `r` | 5–19 | 大量线程排队 |

→ 瓶颈是 **CPU 饱和**，不是数据库或磁盘。2C 混部部署下，读接口容量约 100 QPS，加机器/升配是最直接的扩容手段。

## 4. CI 流水线（GitHub Actions）

| job | 命令 | 覆盖 |
|---|---|---|
| `backend` | `mvn -B clean test` | 71 个单测 |
| `ai-service` | `pytest ai-service -q` | 319 个测试（全离线） |
| `frontend` | `npm ci && npm run build` | 构建验证 |
| `rag-eval` | `run_eval.py --min-recall 0.95`（BM25 离线） | 检索召回门禁 |
| `secrets` | `scripts/check_secrets.sh` | 密钥泄露扫描 |

- 每个 job `timeout-minutes: 15`，四/五个 job 并行；
- 额外做过**干净检出模拟**（剔除 `.venv`/`node_modules`/`data/embeddings`/`target`/`.env` 后复跑）：4 个 job 全部通过，证明 CI 不依赖本地环境；
- CI 使用精简依赖子集（19 个包），冷启动约 2 分钟。

## 5. 复现命令

```bash

cd backend && mvn -B clean verify        # 71 + JaCoCo 报告

python scripts/e2e_ai.py                 # 16 项断言
python scripts/e2e_rag.py                # 5 类 RAG 用例

# 压测（需先起服务并登录拿 token）
python3 docs/loadtest.py --token <token> --levels 1,10,25,50 --duration 15

# CI
gh run list --limit 5                    # 或看 GitHub Actions 页面
```

## 6. 已知局限

1. 压测只覆盖**只读接口**，写接口（借还/预约）未压测，因为会改数据；
2. 压测环境是 **2C1.76G 混部**，数字不代表独立部署时的容量；
3. JaCoCo 总覆盖率 58%，未覆盖部分以 Controller/配置类为主（见 §2.3）；
4. 并发压测期间 AI 服务也在运行，CPU 资源存在竞争。
