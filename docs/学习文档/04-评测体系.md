# 评测体系

> 一句话：**没有评测的 AI 项目只能叫 demo**。评测回答两个问题：它真的有效吗？改一版之后有没有变差？

## 1. 为什么评测是分水岭

- 大多数候选人能说"我做了 RAG"，但说不出"好在哪、差在哪"；
- 面试官追问"效果如何"时，能给出**指标 + 口径 + 复现命令**的人极少；
- 评测能力 = 工程判断力，也是 AI 应用岗最稀缺的能力之一。

## 2. 评测分两层

| 层 | 评测对象 | 不需要 LLM | 指标 |
|---|---|---|---|
| 检索层 | 找没找对资料 | ✅ 纯计算 | Recall@5、MRR |
| 答案层 | 答得对不对/有没有依据 | ❌ 需要 LLM judge | faithfulness、answer_relevancy、context_precision、引用准确率、拒答率 |

## 3. 检索层指标

**Recall@5**：正确答案是否出现在前 5 条结果里。

```
Recall@5 = 命中用例数 / 总用例数
```

**MRR（Mean Reciprocal Rank）**：第一个正确答案排名的倒数，取平均。

```
MRR = mean(1 / rank_first_correct)
例：第 1 名命中 → 1.0；第 2 名 → 0.5；第 5 名 → 0.2；没命中 → 0
```

> 为什么两个都看：Recall 看"有没有找到"，MRR 看"排得好不好"。只 Recall 会掩盖排序问题。

本项目数字：**Recall@5 1.000 / MRR 0.916**（向量检索）。

## 4. 答案层指标（RAGAS 等价，自研）

| 指标 | 含义 | 本项目结果 |
|---|---|---|
| faithfulness | 答案的每个论断是否被检索上下文支持（防幻觉） | **0.940** |
| answer_relevancy | 答案是否切题 | 0.971 |
| context_precision | 召回的上下文里有多少是相关的 | 0.667 |
| 引用准确率 | `[n]` 指向的块是否真的相关 | **0.913** |
| 拒答正确率 | 无依据问题是否正确拒答（且不编造） | **9/10** |

> 为什么自研而不用 RAGAS 库：依赖安装失败（tiktoken 需要联网下 BPE），于是按 RAGAS 指标定义自己实现，反而更可控、更便宜。

## 5. LLM-as-judge 的做法

1. 把「问题 + 模型答案 + 检索证据（含所有工具结果）」交给 judge 模型；
2. 要求输出 JSON：`{"faithfulness": 0~1, "reason": "..."}`（DeepSeek `response_format=json_object`）；
3. 失败重试 3 次 + 断点合并（避免一次网络抖动毁掉整批评测）；
4. **关键细节**：judge 必须看到"该轮模型可见的全部证据"（包括馆藏接口结果），否则库存类问题会被误判为"无依据"（faithfulness=0）——本项目踩过这个坑。

## 6. 评测集设计（85 条）

| 类型 | 数量 | 目的 |
|---|---|---|
| 图书类 | 30 | 书名/作者/库存/详情 |
| FAQ 类 | 30 | 常见问答 |
| 规则类 | 15 | 借阅规则、罚金、预约 |
| 无依据类 | 10 | 验证拒答，防编造 |

**评测口径**：命中判定同时约束 `source_type` 与关键词，避免"只比 chunk_id"导致口径漂移。

## 7. 指标陷阱（面试加分项）

| 陷阱 | 说明 | 本项目的处理 |
|---|---|---|
| 自评偏差 | judge 与生成同源模型会偏袒自己 | 如实写进局限，建议换模型或人工抽检 |
| 评测集泄漏 | 调参时反复看测试集 → 过拟合 | 没有在测试集上调 RRF 权重（本项目明确不做） |
| 多源等价 | 同一答案存在于 rule 和 FAQ，口径太严会误判 | 记录为局限，而不是硬改指标 |
| 样本太少 | 85 条不足以覆盖长尾 | 提高样本多样性，结论标注样本量 |
| 只看平均 | 报喜不报忧 | 同时报 P95 延迟、拒答率、失败率 |

## 8. 把评测变成门禁

- 检索层进 CI：`run_eval.py --min-recall 0.95`，低于阈值构建失败；
- 答案层不进 CI（需要真实 Key、成本高），改成**发版前手动跑**并归档报告；
- 报告合并：支持中断续跑，输出 JSON 可 diff 两版差异。

## 9. 面试追问

**Q1：你怎么证明 RAG 有效？**
> 两层：检索层 Recall@5 1.000 / MRR 0.916；答案层 faithfulness 0.940、引用准确率 0.913、拒答 9/10。85 条评测集，有脚本可复现。

**Q2：faithfulness 怎么算的？**
> 让 judge 模型判断"答案中的每个论断是否被给定证据支持"，输出 0~1 分并给理由；关键是证据要给全（包含工具返回的馆藏数据）。

**Q3：为什么不用 RAGAS？**
> 依赖装不上（tiktoken 需要联网下载 BPE），于是我按 RAGAS 的定义自研了等价指标，成本更低、可控性更强；局限（judge 同源）也写进了报告。

**Q4：评测集怎么保证有代表性？**
> 按问题类型配比（图书/FAQ/规则/拒答），每类从真实使用场景出发；命中判定同时约束来源类型和关键词，避免口径漂移。

**Q5：改了一版 Prompt，怎么知道没退化？**
> 同一评测集重跑，对比 faithfulness / 引用准确率 / 拒答率；检索侧看 Recall/MRR 是否守住门禁。

## 10. 自测题

1. Recall@5 = 1.0 但 MRR 只有 0.5，说明什么？
2. 为什么 judge 需要看到"全部工具结果"？
3. 为什么答案层评测不进 CI？
4. 拒答正确率怎么算？为什么强调"0 编造"？
5. 评测集反复用来调参有什么风险？

<details><summary>参考答案</summary>

1. 正确答案都进了前 5，但普遍排名靠后（平均在第 2 名左右），排序质量一般。
2. 否则 judge 不知道模型当时有哪些证据，会把"有依据的回答"误判为无依据（本项目踩过）。
3. 需要真实模型 Key、成本高、耗时长，不适合每次提交都跑；放在发版前执行并归档报告。
4. 无依据问题中被正确拒答的比例；同时要检查没有编造内容，避免"拒答话术 + 编造细节"。
5. 过拟合：指标变好可能只是适配了测试集，真实效果没变；本项目明确不在测试集上调 RRF 权重。
</details>
