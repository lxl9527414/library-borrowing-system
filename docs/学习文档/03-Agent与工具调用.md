# Agent、工具调用与状态机

> 一句话：Agent = **LLM 做决策 + 工具做执行 + 状态机做约束**。没有约束的 Agent 是 demo，有约束的 Agent 才是产品。

## 1. 为什么需要状态机

一次对话不是"问一次答一次"，而可能是：

```
用户：帮我借红楼梦
  → 查馆藏（工具）
  → 模型决定调 borrow_book（写工具）
  → 暂停，等用户确认
  → 用户确认
  → 恢复，执行借阅（工具）
  → 模型组织自然语言回复
```

这里面有 **多步、有暂停、可失败、要审计**，用裸 while 循环写会失控；用状态机（LangGraph）能显式表达节点、条件分支、中断与恢复。

## 2. LangGraph 核心概念（够用版）

| 概念 | 含义 | 本项目对应 |
|---|---|---|
| State | 贯穿整个执行的共享数据 | 消息、工具结果、usage、步数 |
| Node | 一个处理函数 | `agent`（调模型）、`authorize`（检查写操作）、`tools`（执行工具） |
| Edge | 节点间跳转 | agent → 条件判断 → tools / END |
| interrupt | 暂停并等待外部输入 | 写操作确认 |
| checkpointer | 保存执行进度，支持恢复 | 内存实现（Redis 可选） |

## 3. 本项目状态机

```
        ┌──────────┐
        │  agent   │ 调模型；有工具调用 → 判断读写
        └────┬─────┘
     ┌───────┴────────┐
     ▼                ▼
 只读工具          写工具
     │                │
     ▼                ▼
  tools 执行      authorize 构造确认卡 → interrupt 暂停
     │                │（用户确认后 resume）
     └──────┬─────────┘
            ▼
        回到 agent（最多 8 步）
            ▼
           END（done 事件）
```

**三个硬约束**：

1. `max_steps = 8`：防止无限循环，超步直接收尾并说明；
2. **工具白名单**：模型只能调 7 个已注册工具，未知工具名回灌错误；
3. **参数校验**：`top_k 1~10`、`source_types` 枚举、`bookId` 整数——非法参数不落库。

## 4. 工具设计（7 个）

| 工具 | 读/写 | 说明 |
|---|---|---|
| `search_books` | 读 | 按书名/作者/分类检索馆藏 |
| `get_book_detail` | 读 | 单本详情 + 预约队列 |
| `get_my_borrows` | 读 | 当前用户在借记录 |
| `search_knowledge` | 读 | RAG 知识检索（规则/FAQ/图书） |
| `borrow_book` | **写** | 借书（需确认） |
| `return_book` | **写** | 还书（需确认） |
| `reserve_book` | **写** | 预约（需确认） |

**工具返回的统一结构**：`{ok, data/error, message?, citation_no?}`。
- `ok:true` → 模型基于 data 回答；
- `ok:false` + 中文原因 → 回灌给模型，让它自然解释；
- 鉴权失败（401）→ 直接透传前端要求重新登录，**不让模型圆场**。

## 5. 人在回路（Human-in-the-loop）

### 5.1 为什么必须做

AI 能真实写库，没有确认就可能：误借、误还、批量改数据。确认机制是"AI 能动数据"与"AI 能安全动数据"的分界线。

### 5.2 实现要点

1. 模型产出写工具调用 → `authorize` 节点构造确认 payload（书名/参数/影响）；
2. 调 `interrupt()` 暂停，前端收到 `confirm_required` 弹卡片；
3. 用户点确认 → `POST /api/ai/chat/confirm`；
4. 服务端用 `Command(resume={"approved": true})` 恢复同一 `thread_id`，才真正执行工具。

### 5.3 两个容易被问的细节

- **确认状态存哪**：Redis，TTL 300 秒，**GETDEL 一次性消费**（防重放）；
- **interrupt 恢复会重放节点代码**：所以 `authorize` 必须是**纯计算**（不写存储、不发事件），否则会重复执行副作用。

### 5.4 确认卡的可读性

真实模型跨轮可能只传 `bookId`（上一轮已查过），确认卡就会变成《该图书》。解决：确认前回查一次图书详情补书名（只读、幂等、带缓存），并保留"无书名"兜底模板。

## 6. 错误处理矩阵

| 失败类型 | 处理方式 | 原因 |
|---|---|---|
| 业务失败（无库存/重复借阅） | `ok:false` + 原因回灌模型 | 模型能自然解释，用户可继续 |
| 上游异常（Java 500） | 回灌 + 提示稍后重试 | 不中断对话 |
| 鉴权失败（token 过期） | 401 透传前端 | 不能让模型"圆场"掩盖登录问题 |
| 模型调用超时 | 重试 1 次；已吐 token 则不重试 | 避免重复文本 |
| 工具名不存在 | 回灌 `TOOL_NOT_FOUND`，连续 3 次终止 | 让模型自我纠正 |

## 7. 常见坑

| 坑 | 症状 | 解决 |
|---|---|---|
| 死循环 | 模型反复调同一工具 | max_steps + 重复调用检测 |
| 工具结果过大 | 上下文爆炸、成本飙升 | 结果截断（如知识块 500 字） |
| 模型编造工具名 | 报未知工具 | 白名单 + 错误回灌 |
| 确认被绕过 | 直接调内部接口写库 | 内部接口要求 X-Internal-Token + nginx 封禁 |
| 并发会话串数据 | 两个用户互相看到对方上下文 | sessionId 隔离 + 身份从 token 解析 |
| 工具参数类型错 | 500 | schema 校验 + 类型转换 |

## 8. 面试追问

**Q1：Agent 的循环怎么控制？**
> 三道闸：最大步数 8、工具白名单、错误回灌自愈；连续失败或超步强制收尾，不会无限跑。

**Q2：人在回路具体怎么实现？**
> LangGraph `interrupt()` 暂停并保存确认 payload；前端确认后 `Command(resume=...)` 恢复同一 thread_id；确认状态存 Redis、TTL 300s、GETDEL 一次性消费防重放。

**Q3：怎么防止模型乱调工具？**
> 白名单 + 参数校验 + 读写分类（写操作必须确认）+ 服务端权限拦截（token 只从请求头解析，模型无法伪造 userId）。

**Q4：多步任务失败了怎么恢复？**
> 业务失败回灌给模型继续决策；图执行进度由 checkpointer 保存（当前是内存，换 Redis Stack 可跨重启）；确认状态在 Redis，重启不丢。

**Q5：为什么不用 LangChain 的 AgentExecutor？**
> 它的循环边界、确认中断、审计点不够可控；用 LangGraph 自己搭状态机，节点职责清晰，能加授权节点和确认节点。

## 9. 自测题

1. `interrupt()` 恢复时为什么会"重放"节点？这要求节点满足什么性质？
2. 写操作确认为什么必须服务端做，前端弹窗不行吗？
3. 工具返回 `ok:false` 和抛异常，对模型行为有什么不同？
4. 为什么鉴权失败不交给模型解释？
5. 如何保证两个用户的会话不串？

<details><summary>参考答案</summary>

1. LangGraph 从检查点恢复会重新执行当前节点；因此 `interrupt` 前的代码必须纯（无副作用），副作用放到恢复之后。
2. 前端弹窗可被绕过（直接调接口）；服务端必须自己拦截写操作，前端只是交互层。
3. `ok:false` 是业务结果，模型能继续推理并解释；抛异常会中断流程，模型没有纠正机会。
4. 401 是身份问题，模型无法修复；让它解释会掩盖问题，用户应被引导重新登录。
5. 每次对话用独立 sessionId，身份只从 Authorization token 解析，服务端不信任客户端传的 userId。
</details>
