# 工程化与质量

> 一句话：AI 功能的难点不在"能跑通"，而在**可测试、可观测、可降级、可回滚**。这部分是 Java 背景候选人的优势区。

## 1. 可测试性：怎么让 AI 测试"离线可跑"

AI 代码难测的三个原因：依赖大模型（网络/Key/钱）、依赖数据库/Redis、输出不确定。

本项目的三层替身：

| 依赖 | 替身 | 效果 |
|---|---|---|
| 大模型 | **Mock LLM**（确定性关键词模型） | 无 Key、无网络、结果可断言 |
| Redis | **fakeredis** | 会话/确认状态可单测 |
| 外部 HTTP（Java 内部接口） | **httpx.MockTransport** | 工具调用结果可控 |

最终：**319 个 AI 单测 + 71 个后端单测全离线可跑**，CI 不需要任何 Key。

## 2. 测试金字塔（本项目的四层）

| 层 | 数量 | 内容 |
|---|---|---|
| 单元测试 | 319（AI）+ 71（后端） | 工具、检索、状态机、服务 |
| 端到端脚本 | `e2e_ai.py`（16 项断言）+ `e2e_rag.py`（5 类问题） | 身份透传、确认、落库、引用、拒答 |
| UI 回归 | `ui_screenshot.mjs`（CDP） | 页面渲染、新对话、移动端 |
| 评测门禁 | `run_eval.py --min-recall 0.95` | 检索质量不退化 |

## 3. CI 流水线（5 个 job）

| job | 命令 | 作用 |
|---|---|---|
| backend | `mvn -B clean test` | 71 个后端测试 |
| ai-service | `pytest ai-service -q` | 319 个 AI 测试 |
| frontend | `npm ci && npm run build` | 构建验证 |
| rag-eval | `run_eval.py --min-recall 0.95` | 检索召回门禁 |
| secrets | `check_secrets.sh` | 密钥/凭据扫描 |

> 额外加了 `check_icloud_dups.sh`：防止 iCloud 同步冲突副本被当源码编译（真实踩过的坑）。

## 4. 配置管理

- 所有可变项走环境变量（`.env`），代码不硬编码 Key / token / URL；
- `.env` 与 `credentials.local*` 全部 gitignore；
- AI 服务配置：`config.py` 用 pydantic-settings，自动读仓库根 `.env` 与 `ai-service/.env`；
- 生产配置 `/opt/library/config/ai.env`（600 权限），systemd `EnvironmentFile` 注入。

## 5. 优雅降级（AI 服务挂了业务不能挂）

| 依赖 | 降级行为 |
|---|---|
| 向量检索 | 失败 → BM25 |
| 重排 | 失败 → 原顺序 |
| Redis | 不可用 → 进程内存（并在 health 暴露状态） |
| checkpointer | 缺包 → InMemorySaver |
| 模型 | 超时 → 重试 1 次；主模型失败 → 备用/mock |
| 整个 AI 服务 | 停掉 → 业务功能仍可用，对话页显示未连接 |

## 6. 部署形态（本项目真实部署）

```
Cloudflare → nginx :80 ─┬─ /            → Spring Boot :18080
                        └─ /api/ai/**   → FastAPI :8000（仅 127.0.0.1）
                                            └─ 内部接口 → 18080（带 X-Internal-Token）
```

- systemd 守护；`library-ai` 设 `MemoryLimit=600M` 保护 Java/MySQL；
- 服务器 1.76G 内存，加了 **1GB swap**；
- nginx 对 SSE 关闭 `proxy_buffering`（否则 token 会攒着一起返回）；
- 一键发布/回滚脚本：`deploy/push.sh`、`deploy/push-ai.sh`。

## 7. 可观测性

- 结构化 JSON 日志：`traceId / sessionId / tool / durationMs / code / provider`；
- 同一 traceId 可贯穿"请求 → 模型 → 工具 → 结束"，方便 grep；
- **Langfuse** 埋点：按 ingestion HTTP 协议上报 trace/span/generation，默认 Noop，失败熔断，不拖累主链路；
- 关键指标：TTFT、工具耗时、失败码、token 用量。

## 9. 面试追问

**Q1：AI 服务怎么测试？没有 Key 怎么办？**
> 三层替身：mock LLM（确定性关键词模型）、fakeredis、httpx.MockTransport；319 个单测全离线，CI 不需要 Key。

**Q2：怎么保证改动不破坏效果？**
> 四层：单测 → e2e 脚本 → UI 回归 → 检索评测门禁；其中评测门禁进 CI（Recall ≥ 0.95）。

**Q3：AI 服务挂了怎么办？**
> 业务不受影响（两个进程、nginx 分流）；AI 内部各依赖都有降级：向量→BM25、重排→原序、Redis→内存、checkpointer→内存。

**Q4：线上怎么排查一次对话？**
> 结构化日志按 traceId 串起来：请求、模型耗时、工具调用与耗时、错误码；Langfuse 可看 span 时间线。

**Q5：部署时遇到最大的坑？**
> CentOS 7 glibc 2.17：最新 Miniconda 要 2.28 → 用 24.x；numpy 2 无兼容 wheel → 锁 <2；tiktoken 需 Rust → 锁 0.8.0；还加了 swap 和内存上限防 OOM。

## 10. 自测题

1. 为什么 e2e 测试要能离线跑？依赖真实模型会有什么问题？
2. CI 里加"召回门禁"的意义是什么？
3. 优雅降级和"直接报错"的用户体验差异？
4. 为什么 SSE 代理必须关 buffering？
5. 怎么保证密钥不进仓库？

<details><summary>参考答案</summary>

1. 离线才能进 CI、才能反复跑；真实模型有成本、不稳定、结果不可断言。
2. 防止检索质量悄悄退化（改了切分/参数但没人发现），把"效果"变成构建约束。
3. 降级后核心功能仍可用（如 BM25 兜底、业务不受影响）；直接报错会让用户完全无法使用。
4. nginx 默认会缓冲响应，SSE 的 token 被攒住、一次性返回，失去流式体验。
5. gitignore + 双扫描（工作区/历史）+ CI secrets job + 生产配置 600 权限并只注入环境变量。
</details>
