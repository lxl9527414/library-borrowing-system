# 成本与延迟优化

> 一句话：AI 应用上线后，**成本与延迟就是产品体验的一部分**；能说出"钱花在哪、慢在哪"的人，比只会调 API 的人高一个层级。

## 1. 先定义指标（不然没法优化）

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| **TTFT** | 首 token 时间（用户看到第一个字） | 流式体验的体感核心 |
| 总延迟 | 从请求到 done | 任务完成时间 |
| tokens/s | 输出速度 | 长回答的等待感 |
| 端到端延迟 | 含检索 + 工具 + 多步 Agent | 真实用户等待 |
| 单轮成本 | 输入/输出 token 换算金额 | 商业化可行性 |
| 失败率 / 重试率 | 超时、限流、网络错误 | 隐形成本放大器 |

## 2. 本项目实测（真实采样）

| 指标 | 数值 |
|---|---|
| 模型 TTFT | **P50 897ms / P95 1186ms** |
| 输出速度 | 84.2 字/秒 |
| Agent 端到端 | **P50 2481ms / P95 10654ms** |
| 单轮 token | 输入 4054 / 输出 165 |
| **单轮成本** | **≈¥0.0094**（每千轮 ≈¥9.4） |
| 成本结构 | **96% 在输入** |

## 3. 成本怎么算

```
成本 = 输入 tokens × 输入单价 + 输出 tokens × 输出单价
```

本项目的关键洞察：**输出只有 165 token，输入 4054 token**。所以：

- 降输出长度（少说废话）对成本影响很小；
- **降输入长度才是主要杠杆**：system prompt、工具结果、RAG chunks、历史消息。

## 4. 降本杠杆（按性价比排序）

| 杠杆 | 做法 | 预期收益 | 代价 |
|---|---|---|---|
| 工具结果截断 | 知识块 500 字、列表只返回必要字段 | 输入降 20–40% | 可能丢细节 |
| RAG top-k 控制 | 5 → 3，或按问题类型动态 | 输入降 10–20% | 召回略降 |
| 会话摘要 | 长对话压缩成摘要再带入 | 长会话成本降 50%+ | 实现复杂，可能丢信息 |
| 语义缓存 | 相似问题直接命中缓存 | 重复问题成本≈0 | 需缓存与失效策略 |
| Prompt 精简 | 去掉冗余规则、合并示例 | 输入降 10–30% | 规则表达力下降 |
| 模型分级 | 简单问题用小模型/便宜模型 | 成本降 50%+ | 需要路由与评测 |
| 减少 Agent 步数 | 合并工具、减少往返 | 成本与延迟双降 | 灵活性下降 |

> **不要一次性全上**：每个杠杆都会影响质量，必须用评测验证（见 `04-评测体系.md`）。

## 5. 延迟优化（按见效速度排序）

1. **流式输出（SSE）**：首 token 立即给用户，体感延迟从 2.5s 降到 0.9s；
2. **减少 Agent 步数**：每次工具往返都加一次模型调用，步数是最直接的延迟来源；
3. **检索并行**：向量与 BM25 同时查，而不是串行；
4. **连接复用**：httpx 客户端复用连接，避免每次握手；
5. **预热**：服务启动后加载索引/嵌入模型，避免首个请求慢；
6. **超时与降级**：检索/重排失败快速回退，不拖住用户。

## 6. 权衡表（面试可直接讲）

| 想要 | 代价 | 本项目的选择 |
|---|---|---|
| 更便宜 | 输入变短 → 可能少依据 | 截断工具结果，但保留引用块完整 |
| 更快 | 少检索/少步数 → 质量下降 | 流式 + 限制 8 步，不牺牲引用 |
| 更准 | top-k 更大、重排 → 成本上升 | 评测显示向量单独最好，去掉重排反而更快更省 |
| 更稳 | 重试 → 成本与延迟上升 | 只重试 1 次，已吐 token 不重试 |

## 7. 常见坑

| 坑 | 说明 |
|---|---|
| 重试放大成本 | 一次失败重试 3 次 = 4 倍输入成本；要限制次数并区分"已开始输出" |
| 长上下文惯性 | 多轮对话历史无限增长，成本线性上涨 |
| judge 成本被忽略 | 评测也要花钱，批量评测要用小样本或便宜模型 |
| 只看平均延迟 | P95 才是用户体感（本项目 P95 10.6s，明显高于 P50 2.5s） |
| 模型单价变动 | 成本报告要标注"按当前单价与实测 token 计算" |

## 8. 面试追问

**Q1：你的单轮成本多少？怎么算的？**
> 实测输入 4054 / 输出 165 token，按 DeepSeek 单价折算单轮 ≈¥0.0094；每千轮约 ¥9.4。成本 96% 在输入。

**Q2：怎么降本？**
> 主要砍输入：工具结果截断、RAG top-k 控制、会话摘要、语义缓存、Prompt 精简；输出端收益小。每个杠杆都要用评测验证质量不下降。

**Q3：怎么优化首屏延迟？**
> SSE 流式（TTFT 从 2.5s 降到 0.9s）+ 减少 Agent 步数 + 检索并行 + 连接复用。

**Q4：P95 为什么这么高？**
> DeepSeek 偶发网络错误触发重试，加上多步 Agent（工具往返）叠加；已加超时与降级，但仍记录为已知问题。

**Q5：成本和效果冲突时怎么选？**
> 先定义可接受的质量底线（faithfulness / 引用准确率），在底线之上再降本；本项目保留引用块完整性，只截断非关键字段。

## 9. 自测题

1. 为什么"降输出长度"对成本影响小？
2. 重试为什么会放大成本？什么情况下不该重试？
3. 流式输出优化的是哪个指标？
4. 语义缓存会带来什么风险？
5. P50 与 P95 差距大说明什么？

<details><summary>参考答案</summary>

1. 输出只有 165 token，占比低；输入 4054 token 才是成本主体。
2. 每次重试都重新计费输入；已经开始输出 token 时重试会产生重复文本，应放弃。
3. TTFT（首 token 时间），用户体感从"等 2.5 秒"变成"0.9 秒出字"。
4. 缓存命中错误答案、数据更新后缓存过期，导致答非所问；需要 TTL 与失效策略。
5. 长尾请求（重试、多步、网络抖动）拖慢了部分用户；优化要看 P95 而非只看平均。
</details>
