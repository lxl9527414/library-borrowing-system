# RAG 全链路

> 一句话：RAG = 把"私有知识"塞进模型上下文的技术；难点不在"能检索"，而在**切得对、找得准、引得出、答得实**。

## 1. 全景图（本项目）

```
MySQL 业务数据 + 规则/FAQ 文档
        │  build_corpus.py（一次性构建）
        ▼
  knowledge.jsonl（535 块，带 sha256）
        │  index_corpus.py
        ▼
  向量索引（1024 维，numpy/pgvector）+ BM25 倒排
        │  查询时
        ▼
  向量 Top20 ┐
             ├─ RRF 融合 → gte-rerank（20→5）→ 组装 chunks（带 citation_no）
  BM25 Top20 ┘
        ▼
  作为 tool 结果返回给 Agent → 模型生成带 [n] 引用的回答
```

## 2. 语料构建与切分（本项目 535 块怎么来的）

| 来源 | 数量 | 切分策略 | 为什么 |
|---|---|---|---|
| 图书简介 | 500 | 一本一块 | 简介短，切开反而丢上下文 |
| 借阅规则 | 5 | 按语义段落拆 | 规则条款独立，便于精确命中 |
| FAQ | 30 | 一问一答一块 | 用户问题与 FAQ 高度同构，整块命中最好 |
| **合计** | **535** | — | — |

> 切分的核心矛盾：**块太大 → 噪声多、成本高；块太小 → 语义断裂、检索不到**。本项目按"内容类型"分别定策略，比统一 512 token 更准。

## 3. Embedding

- 模型：通义 `text-embedding-v3`，**1024 维**；
- 归一化后点积 = 余弦相似度（本项目向量已 L2 归一化）；
- 索引大小：535 × 1024 × 4B ≈ 2.2MB（`data/embeddings/*.npz`）；
- 构建耗时：约 18 秒（一次性，有 sha256 校验防止语料/索引不一致）。

## 4. 向量检索

```
query → embedding → 与所有块做余弦 → 排序 → Top-K
```

优点：擅长同义/上位词（"能借多久" ↔ "借阅期限"）；
缺点：**精确词弱**（书名、ISBN、"0.2 元"这类，向量不敏感）。

## 5. BM25（关键词检索）

直觉：一个词在文档中出现越多越相关（TF），但这个词在整个语料中越常见越不具区分度（IDF），并对文档长度做归一化。

```
score = Σ IDF(qi) · [ tf·(k1+1) / (tf + k1·(1 - b + b·|d|/avgdl)) ]
k1=1.5, b=0.75
```

本项目实现要点：`bm25.py` 纯 Python、IDF 做非负截断（避免高频词负分）。

## 6. 混合检索：RRF

```
RRF(d) = Σ 1 / (k + rank_i(d))     k=60
```

- 不看分数只看**排名**，所以天然适合融合"余弦分数"和"BM25 分数"这两种不可比的量纲；
- 两路各取 Top20 融合，再排序取 Top-K。

**为什么两路都留**：向量管同义，BM25 管精确词；评测证明规则类问题 BM25 被同形 FAQ 抢位（MRR 0.394），向量能救回来（0.578）。

## 7. 重排（Rerank）

- 通义 `gte-rerank-v2`：给 query+chunk 打分，比向量余弦更精细；
- **候选池必须够大**：本项目踩过坑——只把 Top5 给重排，重排无法把第 6–20 名捞回来，指标反而下降；改成 **20 候选**后 BM25 从 0.859 → 0.889；
- 但仍没超过纯向量（0.916），原因有两个：① rule/FAQ 多源等价（评测口径要求命中 rule，reranker 只看语义）；② 约 8% 调用失败（网络），失败即回退。

## 8. 生成、引用与拒答

- 工具返回 chunks 时递增 `citation_no`，模型正文用 `[n]` 引用；
- 前端把 `[n]` 渲染成可点击标记，点一下滚动并高亮来源卡；
- 低相关过滤：向量分数 < 0.67（`RAG_TOOL_MIN_SCORE`）直接视为无依据；
- 空 chunks → 模型必须拒答（固定话术）。

## 9. 六档检索评测结果（本项目真实数字）

| 配置 | Recall@5 | MRR |
|---|---|---|
| BM25 | 0.973 | 0.859 |
| BM25 + rerank | 0.973 | 0.889 |
| 向量 | **1.000** | **0.916** |
| 向量 + rerank | 1.000 | 0.897 |
| 混合 RRF | 1.000 | 0.889 |
| 混合 + rerank | 1.000 | 0.887 |

> 结论：**向量单独最好**，所以生产默认 `RAG_RETRIEVAL_MODE=vector`、重排关闭。这个"反直觉"的结论比"堆技术"更有说服力。

## 10. 常见坑

| 坑 | 症状 | 解决 |
|---|---|---|
| 索引与语料不同步 | 检索到已删除的块 | 语料 sha256 写入索引 meta，不一致拒绝加载 |
| 切分过碎 | 检索到半句话 | 按内容类型定策略，块内保留标题 |
| 只给重排 top5 | 重排后指标变差 | 候选池 20 |
| 无降级 | 向量服务挂了整个 RAG 挂 | 向量失败 → BM25；重排失败 → 原序 |
| 引用编号错位 | 引用的 [2] 指向无关内容 | `citation_no` 由服务端递增，前端只渲染真实块 |

## 11. 面试追问

**Q1：RAG 完整链路？**
> 语料构建与切分（535 块）→ 1024 维 embedding 索引 → 向量与 BM25 各取 Top20 → RRF 融合 → gte-rerank（可选）→ 组装带 citation_no 的 chunks → 模型生成并强制 [n] 引用；无依据走拒答。

**Q2：为什么还要 BM25？**
> 向量擅长同义，弱在精确词（书名/ISBN/金额）；BM25 正好互补。评测也验证了：规则类问题 BM25 MRR 只有 0.394（被同形 FAQ 抢位），向量把它拉到 0.578。

**Q3：重排为什么没让指标更好？**
> 候选池太小（原先只有 top5）导致重排无法捞回后面的正确块；改成 20 候选后 BM25 变好，但仍低于纯向量。原因是评测口径把"rule 源"当唯一正解，而 reranker 按语义把等价 FAQ 排前面；另外 8% 调用失败会回退。我把它写成已知局限，没有为了刷分去调参。

**Q4：切分怎么定？**
> 按内容类型：图书简介整本一块、规则按条款拆、FAQ 一问一答一块。统一长度切分会破坏语义完整性。

**Q5：怎么防止检索到不相关内容还硬答？**
> 有最低分阈值（0.67）+ 空结果拒答 + 评测里 10 条无依据问题验证。

## 12. 自测题

1. Recall@5 与 MRR 的区别？为什么两个都要看？
2. RRF 为什么用排名而不是分数？
3. 为什么本项目最终关掉重排？
4. 向量库为什么用 numpy 而不是 pgvector？（提示：环境与部署成本）
5. 引用编号应该由谁生成？为什么？

<details><summary>参考答案</summary>

1. Recall@5 看"正确答案有没有进前 5"（覆盖），MRR 看"第一个正确答案排多靠前"（排序质量）。只 Recall 会掩盖排序差。
2. 余弦分数与 BM25 分数不可比，直接加权需要调参且易过拟合；排名是天然可比的。
3. 评测显示重排未超过纯向量，且引入网络依赖与失败回退；关掉更稳、更省。
4. 部署环境小（2G 内存）+ 语料只有 535 块，numpy 内存检索延迟足够低；pgvector 代码保留，换环境可启用。
5. 服务端按返回顺序递增生成，模型只负责引用；前端只渲染真实块，越界编号不显示——避免模型编造引用。
</details>
