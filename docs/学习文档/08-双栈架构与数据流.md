# 双栈架构与数据流（Java + Python）

> 一句话：Java 管"业务与数据"，Python 管"AI 编排"，两者通过**内部 HTTP 工具接口**通信，Python 不碰数据库。

## 1. 为什么是双栈

| 理由 | 说明 |
|---|---|
| 业务资产在 Java | RBAC、事务、库存并发、预约队列、AOP 审计——重写是净损失 |
| AI 生态在 Python | LangGraph、embedding/rerank SDK、评测工具链 |
| 边界清晰 | AI 只是"会调工具的客户端"，业务规则只有一份实现 |

## 2. 三个进程

| 进程 | 端口 | 职责 |
|---|---|---|
| Java Spring Boot | 18080（仅本机） | 业务、数据、权限、审计 |
| Python FastAPI | 8000（仅本机） | Agent、RAG、LLM 编排 |
| Vue（构建后由 Java 托管） | 5173（dev） | 交互层 |

生产上由 nginx 按路径分流：`/api/ai/**` → 8000，其余 → 18080。

## 3. 一次对话的完整数据流

```
1. 浏览器 POST /api/ai/chat（Authorization: Bearer <token>）
2. nginx → FastAPI :8000
3. FastAPI 从 token 解析身份（不信任 body 里的 userId）
4. LangGraph 调模型 → 模型请求工具
5. 工具执行器调 Java：GET /api/ai/internal/books?keyword=...
   请求头：Authorization: Bearer <用户token> + X-Internal-Token: <共享密钥>
6. Java 校验内部密钥 + 用户 token → 查 MySQL → 返回 JSON
7. Python 把结果回给模型 → 生成回答（带 [n] 引用）
8. 若模型请求写工具 → interrupt 暂停 → 前端确认 → resume → 再调 Java 写接口
9. SSE 流式返回：meta → token... → tool_call/tool_result → done
```

## 4. 三层安全边界

| 层 | 机制 | 防什么 |
|---|---|---|
| 身份 | 只从 `Authorization` token 解析用户 | 模型伪造 userId |
| 服务间 | `X-Internal-Token` 共享密钥 | 外部直接调内部接口 |
| 网络 | nginx 对 `/api/ai/internal/` 返回 404 | 公网访问内部路径 |

**实测**（生产）：缺内部 token → 403；有内部 token 但缺用户态 → 401；公网访问 → 404。

## 5. 为什么 AI 不直连数据库

1. 业务规则只能有一份（借阅上限、库存扣减、预约顺延都在 Java）；
2. 事务与并发控制需要 Java 层的锁/条件更新；
3. 审计日志由 Java AOP 统一记录；
4. 权限模型在 Java（RBAC），AI 复制一份必然分叉。

> 代价：每次工具调用多一次内网 HTTP（实测 10–50ms），可接受。

## 6. 失败与降级矩阵

| 场景 | 表现 | 处理 |
|---|---|---|
| Java 接口 5xx | 工具 `ok:false` | 回灌模型，让它提示稍后重试 |
| Java 401 | 工具失败 | 直接透传前端，要求重新登录 |
| Python 服务挂 | 对话不可用 | 业务页面不受影响（两个进程） |
| 模型超时 | 重试 1 次 | 已吐 token 则不重试 |
| Redis 挂 | 会话降级内存 | health 暴露状态 |

## 7. 部署形态

```
Cloudflare
   │
nginx :80
   ├── /            → 127.0.0.1:18080（library-server）
   └── /api/ai/**   → 127.0.0.1:8000 （library-ai）
                        └── 内部调用 → 18080

systemd 管理：library-server / library-ai / redis-library
内存保护：Java -Xmx384m、Python MemoryLimit=600M、1GB swap
```

## 8. 面试追问

**Q1：为什么不用一种语言？**
> 业务在 Java（事务/权限/审计/71 个测试），AI 生态在 Python（LangGraph/embedding SDK）；双栈的代价是多一个进程和一次 HTTP 调用，换来的是各自的生态与清晰边界。

**Q2：为什么 AI 不直接连数据库？**
> 业务规则、事务、审计、权限都在 Java，复制一份 SQL 必然和业务层分叉；AI 只做编排，数据操作统一走内部工具接口。

**Q3：怎么防止 AI 越权？**
> 三层：身份只从 token 解析（模型无法伪造）、内部接口要共享密钥、nginx 封禁公网内部路径；写操作还要用户确认。

**Q4：两个进程怎么保证一致？**
> 不做分布式事务：每次工具调用是一个短事务（Java 内），AI 层只负责编排与重试；失败回灌让模型解释，最坏情况不产生脏数据。

**Q5：这个架构有什么缺点？**
> 多一次网络往返（10–50ms）、多一个运维对象（Python 服务）、需要同步内部密钥；在小规模下这些成本可以接受。

## 9. 自测题

1. 用户身份在 Python 侧怎么确定？为什么不能用 body 里的 userId？
2. 内部 token 泄露会有什么后果？还有什么兜底？
3. 为什么 nginx 要单独封禁 `/api/ai/internal/`？
4. AI 服务挂掉，业务页面还能用吗？为什么？
5. 双栈架构最大的运维成本是什么？

<details><summary>参考答案</summary>

1. 只从 Authorization token 解析（Redis 会话）；body 里的 userId 可被客户端伪造，模型也可能传错。
2. 可伪造内部调用；兜底是仍需有效用户 token + 写操作确认 + nginx 封禁公网路径。
3. 内部接口只给本机 AI 服务用，公网暴露等于绕过"人在回路"。
4. 能：两个独立进程，nginx 分流，业务不依赖 AI 服务。
5. 多一个服务要部署/监控/升级，且需要维护内部密钥一致性与双端版本兼容。
</details>
