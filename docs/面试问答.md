# 面试问答（20 问）

> 针对"AI 应用开发工程师"岗位，围绕本项目可能被追问的问题。
> 答法原则：**先给结论 → 再给项目里的具体做法 → 最后主动说局限**（主动暴露局限比被问穿更可信）。

---

## A. 架构与选型

### 1. 为什么用 Java + Python 双栈，而不是全 Java 或全 Python？
> 结论：业务资产在 Java，AI 生态在 Python。

- 原系统已经有 RBAC、事务、库存并发、预约队列、AOP 日志，并且有 71 个测试；重写是净损失。
- AI 应用岗主流生态（LangGraph、RAGAS、各种 embedding/rerank SDK）在 Python。
- 双栈不是"炫技"：它逼出了真实工程问题——**跨服务身份透传**（用户 token 透传到 Java 内部接口）和**内部接口防公网**（共享密钥 + nginx 封禁）。这两点面试比"我会用 LangChain"值钱。

**局限**：多一个运行时；用 docker-compose 与 `scripts/dev_up.sh` 抵消。

### 2. 为什么不让 Python 直接连数据库跑 SQL？
> 结论：业务规则只能有一个事实来源。

- 借阅上限、库存扣减、预约顺延这些规则已经在 Java 里被测试和线上验证。
- AI 层复制一遍 SQL，早晚和业务层分叉（典型：AI 扣库存没加乐观锁）。
- 身份也必须在 Java 侧确定：token → `UserSession`，**LLM 传什么 userId 都不采信**（DTO 里干脆没有 userId 字段）。

**代价**：每次工具调用多一次内网 HTTP（实测 10~50 ms），可接受。

### 3. 为什么用 SSE 而不是 WebSocket？
> 结论：交互本质是"一次请求 → 多个事件"的单向流。

- SSE 有事件名、走普通 HTTP（nginx/中间件透明转发）、鉴权就是普通 header；WebSocket 握手带 header 更麻烦。
- 代价：用户点"确认执行"要**另发一个 HTTP 请求**（`/api/ai/chat/confirm`），已用"确认卡 + 独立请求"消化。

## B. Agent 与工具调用

### 4. Agent 的循环是怎么控制的？会不会死循环？
> 三道闸：最大步数、工具白名单、错误回灌。

- 状态机 `agent → authorize → tools → agent`，`max_steps=8` 强制结束并给出说明。
- 工具名必须在白名单（7 个），未知工具回灌 `TOOL_NOT_FOUND` 让模型自我纠正，连续 3 次则终止。
- 工具参数走校验（`top_k` 1~10、source_types 枚举、bookId 整数），非法参数不落库只回灌错误。

### 5. "人在回路"具体怎么实现的？
> LangGraph `interrupt` + 确认状态存储 + 恢复。

1. 模型产出写工具调用 → `authorize` 节点构造确认 payload（含书名/参数），调 `interrupt()` 暂停；
2. 前端收到 `confirm_required` 弹卡片；用户点确认 → `POST /chat/confirm`；
3. 服务用 `Command(resume={"approved": true})` 恢复同一 `thread_id`，才真正执行工具。

**关键细节**：`interrupt()` 前的代码在恢复时会**重放**，所以 `authorize` 节点必须是纯计算（不写存储、不发事件）。确认状态带 TTL 300s、一次性消费（GETDEL）。

### 6. 确认卡片上的书名是怎么来的？模型只传了 bookId 怎么办？
> 这是我真实遇到并修的 bug。

真实模型可能"跨轮"直接调 `borrow_book`（只带 bookId，因为上一轮已经查过库存），导致卡片显示《该图书》。
修法：确认前若本回合消息里找不到书名，回查一次 `get_book_detail`（只读、幂等、带缓存），全链路兜底文案也不再出现"该图书"。

### 7. 如果用户说"帮我借书"但没说是哪本？
> 让模型澄清，而不是猜。

提示词要求参数不全时先追问；工具 schema 里 `bookId` 是必填整数，模型拿不到就会提问。实测"我要还书"而名下有 3 本在借时，真实模型会反问"要还哪一本"——这是正确行为，评测脚本也因此要求先清空在借记录才做确定性断言。

### 8. 工具调用失败了怎么办？
分三类：
- **业务失败**（无库存、重复借阅）：`ok:false + 中文原因`回灌模型，模型自然解释，不中断对话；
- **上游异常**（Java 500）：同样回灌，模型提示"稍后重试"；
- **鉴权失败**（token 过期）：直接把 401 透传给前端，要求重新登录，不进入模型（避免模型"圆场"掩盖问题）。

## C. RAG

### 9. 你的 RAG 完整链路是什么？
> 语料构建 → 切分 → embedding → 向量库 → 混合检索 → 重排 → 生成 → 引用/拒答 → 评测。

- 语料 535 块（图书 500 / 规则 5 / FAQ 30），图书每本一块（简介短不切）、规则按语义拆 5 段、FAQ 一条一块；
- embedding：通义 `text-embedding-v3`（1024 维），索引 535×1024，构建 18.2 s，幂等；
- 检索：BM25 与向量各取 top-20，RRF(k=60) 融合；
- 重排：通义 `gte-rerank-v2`，20 候选 → top-5；
- 生成：强制 `[n]` 引用，chunks 为空必须拒答。

### 10. 为什么还要 BM25？向量不够吗？
> 精确词是向量的弱项。

书名、ISBN、"0.2 元"这类精确词，BM25 命中更稳；向量擅长同义/上位词。评测也印证了：rule 类问题 BM25 的 MRR 只有 0.394（被同形 FAQ 抢位），向量把它拉到 0.578。

### 11. 重排为什么没让指标更好？
> 诚实回答：在我的评测集上没有。

- 加了 20 候选池后，重排让 BM25 从 0.859 提升到 0.889，但**仍低于纯向量 0.916**；
- 原因有两个：① rule 类问题的正确答案同时存在于 rule 块和 FAQ 块，我的评测要求"必须命中 rule 源"，而 reranker 只按语义相关性打分（它把 FAQ 排前面，对用户其实也对）；② 重排有约 8% 调用失败（网络），失败即回退；
- 我没有在 85 条测试集上调 RRF 权重——那是过拟合。正确做法是先修评测口径（允许多源等价），再评估重排真实增益。

### 12. 怎么防止模型编造规则数值？
四层：
1. 提示词：知识类问题必须先调 `search_knowledge`，不得凭记忆作答；
2. 工具阈值：低相关（vector < 0.67）直接返回空 chunks；
3. 拒答策略：chunks 为空必须回复固定话术"馆藏资料里没有找到依据…"；
4. 评测：10 条无依据问题，拒答 9/10，编造 0。

### 13. 引用是怎么做的？怎么保证引用是"真"的？
- 工具返回 `citation_no` 递增的 chunks；模型被要求正文用 `[n]` 且编号必须对应；
- 前端把 `[n]` 渲染成可点击标记，点一下滚动并高亮对应来源卡；无 chunks 时不显示引用区；
- 评测里计算**引用准确率**（`[n]` 指向的块是否被 judge 判为相关）= 0.913。

### 14. RAG 的评测怎么做才可信？
分两层：
- **检索层**（不需要 LLM）：Recall@5 / MRR，85 条评测集，命中判定同时约束 source_type 与关键词，避免"只比 id"；
- **答案层**（LLM-as-judge）：faithfulness / answer_relevancy / context_precision + 拒答正确性；judge 能看到"该轮模型可见的全部证据"（含馆藏接口结果），否则库存类问题会被误判无依据。

**局限**：judge 与生成模型同源（都是 DeepSeek）存在自评偏好，应换模型或人工双盲抽检。

## D. 工程与稳定性

### 15. 没有 API Key 时项目能跑吗？
能。内置 `mock` 模型：确定性关键词模型，覆盖找书/借还/预约/知识库意图。
- 312 个单测全离线（mock + fakeredis + httpx.MockTransport）；
- CI 不需要任何 Key；
- 演示可零成本复现；切真实模型只改 `.env` 两行。

**坑**：mock 只按关键词应答，早期会回落到固定开场白，被误认为"AI 很笨"；已通过徽标、tooltip、兜底文案明确声明"离线 Mock 模式"，并补齐分类/主题识别。

### 16. 会话与服务重启怎么办？
- 会话历史与确认状态存 Redis（`ai:session:*` TTL 3600s、`ai:confirmation:*` TTL 300s，GETDEL 一次性消费）；
- 服务重启后历史可恢复（有验证脚本）；
- Redis 不可用→自动降级进程内存，并在 `/health` 暴露 `sessionStore` 状态。

**遗留**：LangGraph checkpointer 仍是内存（本机 Redis 缺 RediSearch），换 Redis Stack 即启用。

### 17. 模型超时/限流/挂了怎么办？
网关层：超时（60s）、重试（1 次）、降级链（主模型失败切备用，已吐 token 则不重试避免重复文本）；
检索层：向量失败降级 BM25、重排失败回退原顺序、RAG 整体异常降级为空结果并告知模型；
全部降级都在日志里打 `code=RAG_*`，方便排查。

### 18. CI 怎么做的？为什么能离线跑？
四个 job：后端 `mvn clean test`（71）、AI 服务 `pytest`（312）、前端 build、RAG 召回门禁（BM25 离线，`--min-recall 0.95`）。
离线关键：mock 模型 + fakeredis + MockTransport；索引与语料 sha256 绑定，避免误用旧索引。CI 依赖做了子集裁剪（19 个包），冷启动约 2 分钟。

## E. 反思与取舍

### 19. 这个项目最大的技术难点是什么？
> 不是"调通大模型"，而是**让 AI 的行为可验证、可回滚、可解释**。

- 可验证：每个功能都有断言（16 项 Agent E2E、六档检索评测、答案层四指标）；
- 可回滚：写操作确认 + 复用业务事务，最坏情况不产生脏数据；
- 可解释：工具调用轨迹、引用来源、traceId/耗时/token 全在前端可见。

### 20. 如果重做一次，你会改什么？
1. **先定评测口径再调算法**：rule/FAQ 多源等价应该在评测集里就允许，否则指标会误导优化方向；
2. **早点接真实模型**：mock 掩盖了"跨轮只传 bookId""多轮澄清"等真实行为；
3. **凭据从第一天就注入式管理**：明文凭据文件是隐患（本项目已暴露并计划轮换）；
4. **重排/向量这类"可选增强"一开始就做成可开关**（本项目做到了，但候选池大小这类细节仍是 bug 源）。
